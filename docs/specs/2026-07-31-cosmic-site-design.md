# 宇宙探索（月球）規劃站 — 設計 spec

## 目標

繁中服「宇宙探索」（月球 / 渴望灣）沒有可查的規劃工具。Owner 的原始需求是
「自動偵測各伺服器緊急任務的時間，還有天氣任務的時間」，並在勘查後明確收斂為
**「先確認離線情況下能做到哪個部分，不要有人主動偵測」**。

本 cycle 只做**純離線、零回報者**能成立的部分。

## 勘查結論（動工前的離線查證，全部有實跑證據）

探針＝一次性工具，跑在台服 client `2026.07.22.0000.0000` 的 sqpack 上。

### 能離線算的

| 項目 | 依據 |
|---|---|
| 渴望灣一般天氣（月塵 15%／晴朗 70%／靈風 15%） | `TerritoryType#1237` c12 → `WeatherRate#169`。全 1234 筆 territory 的 c12 無一越界；171/172 筆 rate 總和恰為 100 |
| 天氣演算法正確性 | 用同一條鏈回推中薩納蘭與摩杜納，與既有 `ffxiv-tw-sightseeing/modules/weather.js` 手打表**逐項一致** |
| 全服同步 | 天氣是 unix 時間的純函數，與伺服器 / DC / 實例無關 ⇒ 「各伺服器」這個維度不存在 |
| 101 個任務的 ET 時段條件 | `WKSMissionLotterySpecialCond` row 1–12＝2 小時階梯 |
| 11 個緊急任務的天候條件（靈風） | 同表 row 13 c2＝49（靈風）、row 14＝148（月塵）——**2/2 命中渴望灣天氣表裡的兩個非「晴朗」天氣**，是此欄為天氣 FK 的關鍵佐證 |
| 544 個任務的完整屬性 | `WKSMissionUnit` ＋ `WKSMissionToDo` ＋ `WKSMissionReward`（欄位索引沿用 ICE fork 的反解，見 [P-005 plan](../../../../XIVpluginsDev/docs/plans/2026-07-30-P005-ice-cosmic-tc-fork-plan.md) §1）|
| 宇宙工具 11 職 × 9 階升級鏈 | `WKSCosmoToolClass` c14–c22；道具名逐職吻合（手鋸＝木工、圓革刀＝皮革） |

### 不能離線算的（決定性證據）

緊急事件天氣 `Weather#194/195/196/197`（流星雨 ×2、磁暴、孢子霧）**不出現在 client 全部 172 張
`WeatherRate` 的任何一列**。時間演算法的輸出必須落在某張 rate 表內 ⇒ 它永遠不可能擲出這四個天氣
⇒ 緊急事件只能由伺服器推播。再加上每伺服器每實例各自計時，離線網站對「哪一台、何時」零資訊。

**唯一能給的離線線索＝必要條件視窗**：11 個緊急任務只在靈風時段成立，視窗外一定不出現。

## 範圍

**做**：三分頁靜態站（天氣時間軸／任務清單／宇宙工具）＋ 從 client 產生資料的 C# 工具。
**不做**：緊急任務即時偵測（需插件回報後端，架構上是後掛的一層，不影響本站設計）。

## 關鍵決策

### D1：資料由產生器產出並 commit，不在瀏覽器解析

`data/*.json` 是產物。理由：解 sqpack 需要遊戲 client，且產生器有健全性閘（544／100%／11×9），
任一不過就整批不寫檔——避免半殘資料被 commit。網站因此零外部依賴、可完全靜態託管。

### D2：欄位索引不在本 repo 複製一份

`WKSMission*` 三張表的欄位索引唯一定義在 ICE fork，由 csproj `<Compile Include>` 直接編譯。
產生器本來就只能在有遊戲 client 的本機跑，依賴本機路徑可接受；抄第二份的代價是台服改版後兩邊漂移，
而漂移的症狀是「數字看起來合理但是錯的」。

### D3：未定性欄位一律標明，不填合理值

見 `AGENTS.md` 鐵則 2 的表。**由來是 ICE 那輪連續五次拿 0 當佔位**（`MapPosition` 讓採集完全不執行、
`missionText` 讓技能完全不放），0 在這批 sheet 裡是有意義的哨兵值。在網站上的同型錯誤形式是
「把 6 個條件未定的緊急任務標成隨時可接」。

### D4：金色高亮只給靈風視窗

設計系統的用量上限是「一頁最多 1 處」。這頁真正要盯的就是靈風視窗（限時語意，且是 11 個緊急任務的
必要條件），其餘一律 cyan。

### D5：天氣引擎在本 repo 各自實作，以 BACKLOG 追蹤收斂

`ffxiv-tw-sightseeing` 有一份同演算法的實作。差異在它把演算法與**手打的**全區機率表綁在一起，
而本站的表由 client 產生。收斂到 portal 共用層要動共用 API（Owner Gate1），故先各自實作。
勘查中順帶發現該手打表的**月夜峰那列是錯的**（見 B-001）。

## 驗證

- 產生器健全性閘：544 任務／天氣總和 100%／11 條 ×9 階 — 全過
- 瀏覽器（1920×1080）：三分頁皆正常、console 零 error、水平溢出 0、`.page-header` top=64 高=51（生態基準值）
- 天候篩選實測：11 筆全為緊急、全為「天候：靈風」、靈風時段內全部標「可接」
- design-lint `--strict`：見 CHANGELOG

## 風險與回滾

- **台服改版使欄位索引失效**：症狀通常是產生器健全性閘直接紅（任務數不是 544），不會靜默。
  修法＝先跑 ICE 的 `tc-sheet-verify` 重驗那三張表。
- **回滾**：`data/*.json` 在 git 內，`git checkout` 上一版即可；網站本身無狀態。
